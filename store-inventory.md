## Legend

Classification is exactly one of: **VERIFIED CURRENT**, **LEGACY**, **IN-FLIGHT MIGRATION**,
**TARGET ARCHITECTURE**, **OPEN QUESTION**, **CONTRADICTED BY SOURCE**. Org column: **Y** =
organization_id present on the row itself, **PARENT** = present on a containing/parent doc
only, not the row, **N** = absent everywhere in this collection (and, where the backing model
was read directly this pass, absent from the schema itself — not just unused), **N/A** = not
applicable. **Rules** column (new this pass): the actual Firestore client-side security-rule
verdict for that collection, from `olbrain-studio`'s `firestore.rules` — this is a *different,
narrower* enforcement layer than the "App-layer auth" column, which only covers each owning

## Cross-Repo Flows (verified)

*(Items 1–9 carried over unchanged from the first pass — see history in `investigation/MASTER.md` — new items below.)*

10. **THREE independent writers into `agent_datastores`, all on the identical flat top-level path, all reproducing the same org-on-table-not-entry pattern.** agent-runtime's extract-mode (person-keyed) writer, agent-runtime's live-tool (session-keyed) writer, and agent-design's `routers/datastore.py`/`datastore_service.py` operator-authored writer — three separately-authored code paths in two repos, none of which ever puts `organization_id` on the entry document, only on the parent table doc. This is now confirmed as a genuinely repeated architectural pattern (not two instances, three), and the entry-id hash (`person_hash()`, confirmed unsalted in `olbrain-shared`) is shared identically across all three.
11. **`olbrain-agent-design` is the actual writer/publisher behind every config-path finding agent-runtime could only see from the read side.** Confirmed identical GCS path (`configs/{agent_id}/active_config.json`), confirmed zero cache-invalidation signal on publish (no Pub/Sub, ETag, or versioned path anywhere in the publish/activate/rollback flow), confirmed the exact 3-field org-resolution precedence used for knowledge-base wiring (`tenant_id > organization_id > primaryOrganization` — a *subset* of, not a *disagreement* with, knowledge-vault's own 5-field chain — the risk is coverage gap, not wrong-org resolution), and confirmed `pool_ref`/`cred_source` are dead on the write side too, matching agent-runtime's read-side finding exactly.
12. **`olbrain-studio-backend`'s `agent_transfer_service.py` is the single cascade governing cross-org agent moves — and it is narrower than the six-repo store map assumed.** It cascades (in various forms — copy, re-label, disable, or archive-then-delete): DCI corpus (copy), `agent_sessions` (re-label, ungated even on same-org moves), `workflow_agent_memory` (archive+delete via workflow-runtime's own confirmed endpoint), `knowledge_library` (repoint or detach), `agents/{id}/mcp_configs/*` (soft-disable), usage/analytics rollups (archive). It does **NOT** cascade to `agent_datastores` or `agent_learned_patterns` at all (zero references anywhere in this repo) — these two stores follow an agent across an org transfer with no mitigation whatsoever, unlike `workflow_agent_memory`, which at least gets archived.
13. **`olbrain-shared` is confirmed as the actual, sole model-defining package behind every "field list unconfirmed" open question from the first pass.** All models read directly (`extra="forbid"` on most, meaning the field lists are provably complete, not usage-inferred): `TemplateMeta`, `TemplateBody`, `RunMeta`, `LearnedProfile`, `LearnedItem`, `LearnedDesign`, `LearnedDesignItem`, `LedgerEntry`, `LearnedSubstanceOverride`, `AgentMemory`, `ExceptionPattern`, `LearnedOverride`. None of the "learned"/"memory" models across either domain (research or workflow) carries an organization field — this is now a schema-enforced fact, not merely an observed usage pattern.
14. **The `is_enabled` vs `enabled` MCP-config spelling split remains genuinely unresolved after four repos.** Agent-design (the confirmed writer) only ever writes `enabled`. Agent-runtime's read path falls back to `is_enabled or enabled`. Neither repo investigated is the source of the `is_enabled` variant — it is either dead legacy data sitting in already-published Firestore documents from a pre-agent-design write path, or a third, still-unidentified writer.

**E. RESOLVED — the Firestore catch-all claim is CONFIRMED, and is worse than the senior review stated, with one significant exception.**

**F. Deletion/erasure coverage, revised with cascade data.** The org-transfer cascade (`_ORG_SCOPED_TEARDOWN_STEPS`) covers DCI corpus (copy), `agent_sessions` (re-label), `workflow_agent_memory` (archive+delete), `knowledge_library` (repoint/detach), `agents/{id}/mcp_configs/*` (disable), and usage rollups (archive) — but explicitly **excludes** `agent_datastores` and `agent_learned_patterns` entirely (zero references anywhere in the cascade code). Separately and more fundamentally: **there is no hard organization-delete capability anywhere in the platform** — `archive_organization`/`restore_organization` is a pure status-flip on `projects`/`agents` and is **completely disjoint** from the transfer cascade; archiving an org touches none of the memory/knowledge/MCP stores an agent transfer does. `organization_documents` is the one genuine hard-delete-plus-deindex path found anywhere in this investigation.

**G. (new) The rules-layer exposure and the REST-layer authorization gaps are independent, compounding failures, not overlapping ones.** `workflow_agent_memory` (no REST auth, first pass) and `context_facts`/`context_guardrails`/`vibe_sessions` (dark/fail-closed application CRUD, first pass) all *also* have no Firestore rule at all — meaning the application-layer control (however strict or absent) can be bypassed entirely by a browser client calling the Firestore SDK directly. Fixing the REST layer alone, for any of these stores, would not fix the actual exposure.

**H. (new) Where the platform's authorization design is provably intentional and working, it is genuinely solid.** `agent_datastores`' Firestore lockdown (tested, deliberate, complete), `agent_user_memory`'s org-scoped read rule, `organization_api_keys`' IDOR-safe revoke flow, `organization_documents`' hard-delete-plus-deindex, and the Clix dedicated-tenant ruleset (genuinely default-deny, its own separately-maintained `isOrgMember`, deployed to an isolated GCP project) are all evidence the team can and does build this correctly when they get to it. The problem is coverage and prioritization, not a lack of institutional knowledge of how to do it right.
