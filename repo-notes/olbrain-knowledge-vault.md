## What this service actually is

`README.md` itself is uninformative (`# Staging environment`, 1 line). The real description is in `main.py:121-126`: a FastAPI app titled **"Alchemist Knowledge Vault"**, `version="4.0.0"`, described as "Document processing and semantic search service."

Contrary to the soul map's implicit framing (a single "knowledge corpora" store queried by embeddings), this service is **two generations of system layered together**:

1. A **legacy Firestore-metadata + Firestore-embeddings design** (`KNOWLEDGE_LIBRARY_SCHEMA.md`, `constants/collections.py:KNOWLEDGE_EMBEDDINGS`) where per-chunk embeddings were base64-encoded and stored as Firestore documents (`knowledge_embeddings/{agent_id}/chunks/{chunk_id}`). Confirmed **dead**: `grep -rn "knowledge_embeddings" --include=*.py .` returns only the unused constant definition (`constants/collections.py:10`) — nothing reads or writes it. There was also an even older OpenAI Assistants Vector Store integration (billing/usage tracking in `SNAPSHOT_SYSTEM_REMOVAL_COMPLETE.md`, confirmed retired by `services/file_service.py:1596`: *"Historically this also tore down per-agent OpenAI Vector Stores — that path is gone now that ingestion is DCI-only."*).
2. The **current system**: **DCI** ("Document Corpus Intelligence" — full name not spelled out, but the module/route naming is consistent throughout `services/dci/`, `routes/dci.py`, `docs/dci-contract.md`). DCI stores raw extracted **text files in GCS** (not vector embeddings) under tenant-scoped prefixes, and agents query them via regex grep, span-read, list, and an agentic "ask" endpoint (an in-vault Haiku sub-agent that does iterative grep/read, or a deterministic table/SQL lane, or an FTS-indexed "routed" lane). This is a fundamentally different retrieval model than the soul map's implicit "vector store" framing — it is **not** semantic/embedding search by default; it's regex + LLM-agentic reading over plain text, with a growing set of specialized lanes (`mode`: `tables` | `routed` | `whole` | `agentic`).

Firestore is still used, but only for **metadata** (`knowledge_library` collection) and **auth/API-key** bookkeeping — the actual corpus bytes and searchable text live in GCS (`gs://olbrain-kb` by default, `services/dci/tenancy.py:87-92`, overridable via `DCI_GCS_BUCKET`).

## Store 1: `knowledge_library` (Firestore) — knowledge metadata

- **Path**: Firestore collection `knowledge_library` (`constants/collections.py:9`), one doc per uploaded file/URL/attachment, doc id = `knowledge_id` (uuid4).
- **Writers**: `services/file_service.py` — `upload_file_by_agent` (~line 1772 dual-write call site), `add_url_to_knowledge_base` (line 1677, dual-write at 1931), `add_attachment_to_knowledge_base` (line 2040, dual-write at 2098), `add_processed_file_to_knowledge_base` (line 2217-2382, writes doc at `firebase_service.create_file_by_agent`, line 2359). All routed through `routes/files.py` (`POST /knowledge-base/upload`, `/knowledge-base/add-url`, `/knowledge-base/add-attachment`, `/knowledge-base/add-processed-file`, lines ~85-296).
- **Readers**: `routes/files.py:list_files` (line 326), `get_file_status` (356), `download_knowledge_file` (497); also read by the backfill tools (`tools/backfill_dci_corpus.py`, `tools/backfill_org_corpus.py`) to find un-ingested rows.
- **Data shape** (per `models/file.py` and `KNOWLEDGE_LIBRARY_SCHEMA.md`): `knowledge_id`, `agent_id`, `owner_id`, `created_by`, `status` (active/deleted), `knowledge_info` (filename, content_type file|url, file_size, file_type, mime_type, source_url when applicable), `dci_status` (ready/failed — "DCI source of truth" per `models/file.py:23`), `storage_path` (pointer into Firebase Storage, not the DCI corpus), `created_at`/`updated_at` server timestamps. **No `organization_id` field on the doc itself** — org is never stored redundantly here; it is resolved dynamically from the owning agent's Firestore doc via `resolve_agent_org_id` (`services/dci/tenancy.py:247-265`) every time it's needed. `KNOWLEDGE_LIBRARY_SCHEMA.md`'s documented `organization_id` field and `embeddings_meta`/`usage_metadata` sub-objects reflect the **legacy v3-era schema** and are stale relative to `models/file.py`'s current, simpler shape (comment at `constants/collections.py:9`: "v4.0.0: Simplified knowledge management with direct agent assignment").
- **Scope**: agent (every doc carries `agent_id`; org is derived transitively through the agent).
- **Organization binding**: indirect only — via the agent doc's `resolve_agent_org_id` 5-field precedence (`tenant_id > organization_id > primaryOrganization > org_id > owner_id`, `services/dci/tenancy.py:238-244`). `routes/files.py:_reject_unresolvable_org` (lines 20-42) refuses ingestion for an agent whose org can't be resolved, specifically to avoid a corpus write that agent-runtime's compiler (a **3-field** precedence, no `org_id`/`owner_id` fallback) could never read back — a documented cross-repo precedence mismatch risk, not itself a bug in this repo.
- **PII**: varies by upload — arbitrary documents/URLs a customer or agent operator chooses to upload to an agent's knowledge base. `text_snippet`/`summary` in the legacy schema held up to 1500 chars of extracted content; the current schema (`models/file.py`) drops those two fields from the canonical model (still declared `Optional` but not populated by the write paths read). No evidence found of automated PII scanning/redaction anywhere in this repo.
- **Authorization**: `verify_firebase_token` (Firebase ID token or `ApiKey` header, `middleware/auth.py:115-252`) + a per-request ownership/membership check via `assert_agent_access` (`services/file_service.py:182-240`) and `assert_file_access` (243-274). `assert_agent_access` allows the agent's owner, or an **active member of the agent's org** (mirrors `olbrain-studio-backend`'s `org_roles.is_org_member`); for API-key callers it additionally requires the key's own `organization_id` to equal the agent's resolved org (lines 217-223) — closing a cross-org privilege-escalation gap that would otherwise exist for a key's creating user. Denial paths uniformly raise `ResourceNotFoundError` (not `PermissionDenied`) to avoid leaking existence of agents/files the caller can't access (lines 208-209, 268-273).
- **Deletion/retention**: soft delete only. `delete_file` route (`routes/files.py:387-450`) and `reset_agent_knowledge_base` (`services/file_service.py:1581-1654`) set `status: "deleted"`, `deleted_at`, `deleted_by` — the Firestore doc is never hard-deleted. Both also attempt to remove the corresponding text from the GCS corpus (see Store 2) and explicitly report `corpus_failed`/non-removal back to the caller rather than silently claiming a clean wipe (`services/file_service.py:1592-1596`, `routes/files.py:412-426`).
- **Classification**: **VERIFIED CURRENT** for the `knowledge_library` collection and its write/read/auth paths as described. **LEGACY** for the `knowledge_embeddings` collection and the OpenAI Vector Store integration described in `KNOWLEDGE_LIBRARY_SCHEMA.md` / `SNAPSHOT_SYSTEM_REMOVAL_COMPLETE.md` — dead code paths, not reachable from any current route.

## Store 2: DCI corpus (GCS) — the actual searchable knowledge store

- **Path**: GCS bucket `gs://olbrain-kb` (default; `services/dci/tenancy.py:87-92`, env `DCI_GCS_BUCKET`), object prefix = `resolve_corpus_prefix(org_id, agent_id, corpus_id)` (`services/dci/tenancy.py:162-229`):
  - Agent corpus: `{org_id}/{agent_id}/` (text under `.../text/`, raw bytes under `.../raw/`, metadata under `.../_meta/`, catalog at `.../catalog.json` — comment at `tools/backfill_org_corpus.py` header and `services/file_service.py:511-548`).
  - Org-wide corpus: `{org_id}/_org/` (`tenancy.py:39-48`, reserved segment `_org`).
  - Client/project corpus: `{org_id}/_client/{client_key}/` (`tenancy.py:56-79`).
  - Platform skill corpus: `{DCI_SKILLS_ROOT or "_skills"}/{skill_id}/` (`tenancy.py:21-29, 225-229`).
  - This is a **5-way scope model** (agent, org, client, skill, and the reserved-namespace guards preventing collision between them) — broader than the soul map's "org, agent, skill" claim, which misses the client-corpus scope entirely.
- **Writers**: `services/file_service.py:_dci_dual_write` (479-548) and `_dci_write_to_prefix` (550+), called from every ingestion route (`upload_file_by_agent`, `add_url_to_knowledge_base`, `add_attachment_to_knowledge_base`, `add_processed_file_to_knowledge_base`). Org-corpus and client-corpus writes go through `routes/dci.py` (`POST /api/dci/orgs/{org_id}/ingest` line 444, `POST /api/dci/clients/{client_key}/ingest` line 547), gated by dedicated OIDC allowlists. Skill-corpus writes go through `POST /api/dci/skills/{skill_id}/ingest` (line 409), gated by `verify_curator_caller`. Writes are content-addressed and idempotent: `source_id = sha256(raw_bytes)[:32]` (`services/file_service.py:590`), so re-uploading identical bytes is a no-op / re-enable rather than a duplicate.
- **Readers**: `olbrain-agent-runtime`'s `core/dci/` module (per `docs/dci-contract.md:7`) calling `POST /api/dci/{grep,read,list,head,ask}` (`routes/dci.py:301-407`). Also internal: `tools/backfill_dci_artifacts.py`, `services/dci/artifact_builder.py` (index-card + FTS artifact generation), `services/dci/ask_service.py` (the agentic/tables/routed retrieval lanes).
- **Data shape**: plain extracted text per source (markitdown-converted for pdf/docx/pptx/xlsx/html/epub, raw utf-8 decode fallback — `services/file_service.py:276-288`), a per-prefix `catalog.json` (source id → path/enabled/ext/hash metadata), optional per-source "index cards" and a SQLite FTS index (`services/dci/index_cards.py`, `services/dci/fts_index.py`) for the "routed" ask lane, and DuckDB-backed spreadsheet querying for the "tables" lane (`services/tables/`). **Not** vector embeddings — no embedding storage exists in the current write path.
- **Scope**: agent / org / client / skill (see prefix scheme above).
- **Organization binding**: for agent corpora, resolved server-side from the agent's Firestore doc (`resolve_agent_org_id`), never trusted from the caller (`services/file_service.py:515-526`: the uploading user's own org, `org_id_hint`, is explicitly NOT used for placement, to prevent corpus-splitting). For org/client corpora, `org_id` is a required body field validated by `resolve_corpus_prefix` and enforced structurally: a real `organization_id` can never equal the reserved `_skills` segment (`tenancy.py:43-47, 187-191`), and a corpus_id of kind `org:` must name the caller's own org (`tenancy.py:212-219`) — a cross-tenant `org:` corpus_id is rejected before any GCS access.
- **PII**: same content-dependent risk as Store 1 — whatever documents/URLs/attachments an org or agent operator ingests. The org corpus is explicitly sourced from `organization_documents` (a Firestore collection **owned by another repo**, likely `olbrain-studio-backend` — confirmed only as a read target in `tools/backfill_org_corpus.py:24`, not owned or defined here) — **OPEN QUESTION**: what PII that collection itself contains is out of scope for this repo and unverified from this source alone.
- **Authorization** (per `docs/dci-contract.md`, verified against `middleware/auth.py:255-470`):
  - Query endpoints (`grep`/`read`/`list`/`head`/`ask`) — **Google OIDC only**, no Firebase token, no API key, no `X-User-Authorization` (`middleware/auth.py:392-407`, confirms `docs/dci-contract.md:21-29`). Token's `email` claim must be in `DCI_RUNTIME_SA_EMAILS`; empty/unset env → every call `503` (`middleware/auth.py:339-347`). The verified `ServiceCallerContext` carries **no** org/agent — `org_id`/`agent_id` come from the request body and are enforced purely by server-side GCS-prefix construction (`resolve_corpus_prefix`) plus `validate_path` blocking traversal in the LLM-supplied `file` argument (`services/dci/tenancy.py:100-159`). This matches the soul map's "OIDC, org-enforced server side" claim, but **only for this one path** — see corrections below.
  - Skill ingestion — separate `DCI_CURATOR_SA_EMAILS` allowlist (`middleware/auth.py:283-290, 410-420`).
  - Corpus relocation (agent moved between orgs) — separate `DCI_RELOCATION_SA_EMAILS` allowlist (293-309, 423-439), driven by `olbrain-studio-backend`.
  - Org-corpus ingest — separate `DCI_ORG_INGEST_SA_EMAILS` allowlist (312-328, 442-449). Comment at 320-324 notes this SA overlaps with the runtime read SA in practice (`olbrain-runtime-sa@`) but the list separation still guarantees the runtime read SA can never write an org corpus.
  - Client-corpus ingest — separate `DCI_CLIENT_INGEST_SA_EMAILS` allowlist (452-470).
  - **Five distinct OIDC allowlists total**, each independently configurable and independently disabled (→ `503`) if unset — a materially more granular model than the soul map's single "OIDC, org-enforced" line suggests.
  - Studio-driven ingestion (upload/add-url/add-attachment/add-processed-file) is **not** OIDC at all — it's the Firebase-token + `assert_agent_access` path described under Store 1.
- **Deletion/retention**: per-source only, never a prefix wipe. `services/file_service.py:delete_from_corpus` (979-1018) and `_delete_source_at_prefix` remove the specific text blob keyed by `sha256(raw_bytes)`, then update `catalog.json`; explicitly documented as "never raises" so a GCS outage can't block the Firestore-side delete (990-993). `reset_agent_knowledge_base` (1581-1654) does this per-file for every active row rather than deleting the whole prefix, because a prefix can also hold a skill corpus or already-soft-deleted rows it doesn't own (1586-1589). **Corpus relocation never deletes the source prefix** — `services/dci/corpus_relocation.py:1-23`: "The source is never deleted. Reclaiming it is a separate, later decision (a lifecycle rule or a reaper)" — i.e., a stranded/orphaned corpus can persist indefinitely after an org-move, by design, pending a reaper that does not exist in this repo. **No org-deletion cascade found**: `grep` for org-deletion/cascade logic in this repo turns up only the relocation module's own docstring; there is no endpoint or trigger here that wipes an org's `_org`/`_client`/agent corpora when an organization is deleted. Whether `olbrain-studio-backend` calls the existing per-source delete endpoints during org deletion is **unverifiable from this repo alone**.
- **Classification**: **VERIFIED CURRENT** — this is the live, only-currently-functional knowledge retrieval mechanism (per `services/file_service.py:1596`, ingestion is "DCI-only" now).

## Store 3: `organization_api_keys` (Firestore) — API-key auth

- **Path**: Firestore collection `organization_api_keys` (`middleware/auth.py:65`).
- **Writer**: not in this repo (queried only; likely provisioned by `olbrain-studio-backend` — **OPEN QUESTION**, not verified here).
- **Reader**: `middleware/auth.py:verify_api_key` (47-112) — looked up by `sha256(api_key)` hash, `status == "active"`.
- **Data shape**: `key_hash`, `status`, `user_id`, `organization_id`, `expires_at`, `last_used_at`, `usage_count`.
- **Scope/org binding**: one org per key (`organization_id` field, directly authoritative — used as-is in `assert_agent_access`'s api-key branch).
- **PII**: low — operational/billing metadata, not end-user content.
- **Authorization**: the API key itself IS the credential; usage is updated non-blocking on each use (92-98).
- **Deletion/retention**: no delete/rotation code found in this repo; `expires_at` is checked but not enforced by any expiry job here.
- **Classification**: **VERIFIED CURRENT** (as an auth store), **OPEN QUESTION** for its lifecycle/ownership (provisioning repo unverified).

## Open Questions

1. Who provisions/rotates `organization_api_keys` docs, and is there an expiry-enforcement job anywhere in the platform? Not in this repo.
2. Does `olbrain-studio-backend` (or any other caller) actually invoke this repo's per-source delete endpoints when an organization or agent is deleted, or does deleted-org data become permanently orphaned in `gs://olbrain-kb`? 3. What does `organization_documents` (the Firestore collection backing the org-wide corpus, per `tools/backfill_org_corpus.py:24`) actually contain, who writes it, and what auth guards it? Owned by another repo, not verifiable from source here.
4. Is `resources.knowledge_base.gcs_prefix` a field agent-runtime actually persists (e.g., in agent config/resources), and if so, does its value match what `resolve_corpus_prefix` would compute server-side, or can it drift? Requires reading `olbrain-agent-runtime`'s `core/dci/` module and `agent-design`'s `config_generator_service.py:834` (referenced at `routes/files.py:20-42` as having a narrower, 3-field org-resolution precedence than this repo's 5-field `resolve_agent_org_id` — a documented, in-repo-acknowledged cross-repo mismatch risk, not yet independently verified against the runtime source).
5. Retention: no TTL/expiry mechanism found for any store in this repo (soft-deleted `knowledge_library` rows and orphaned GCS blobs both appear to persist indefinitely absent a manual reaper).
